# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Read `../CLAUDE.md` first: it describes the surrounding workspace (independent repos, directory ↔ artifactId
mapping, cross-repo dependency propagation). This directory is `globs-shared` on disk but builds
`org.globsframework:globs-off-heap`, currently `5.9-SNAPSHOT`, against `globs` 5.10.0.

## Build & test

Java 22 source/target (local JDK is 25). No CI workflow and no `settings.xml` in this repo — resolution is
`~/.m2` or GitHub Packages.

```bash
mvn -o test                                  # full suite, ~2-3 min (SearchTest/TestShared are perf-heavy)
mvn -o test -Dtest=SearchTest                # one class
mvn -o test -Dtest=OffHeapHashServiceImplTest#withSameHash
mvn -o test-compile
```

Surefire runs with `useModulePath=false` (the Foreign Memory API + unnamed module). Tests are JUnit 5.
`FindPerf`, `ReadPerf` and `ReadAllPerf` are JMH benchmarks (`@Benchmark`, generated by the annotation
processor on the test classpath); there is no runner `main` and no shade plugin, so run them from the IDE or
with an explicit classpath through `org.openjdk.jmh.Main`. `FindPerf` measures the index descent alone;
`ReadPerf` measures what an application does with the offset it gets back — see "What a read costs" below;
`ReadAllPerf` compares the two walks of `readAll` (see "The generated walk"). `OffHeapExample` is the README
example as a `main`, not a test.

`ReadPerf` reads **four different GlobTypes** in round-robin (`PerfTypeFamily`) and runs over a `shape` param
(`narrow` = the 15 fields of `TestShared.DummyObject1`, `wide` = 45). Both axes matter and neither is
decoration: going from one type to four costs `read` 27 % and `find` **60 %**, so any number measured on a
single type is an upper bound nothing in production will see. Numbers from before that change (`read` at
2537 k) are not comparable with the ones below.

Several tests write to fixed paths (`/tmp/test`, `/tmp/testEmpty`, `/tmp/offheap-example`) and reuse them
across classes; newer ones use `Files.createTempDirectory`. Prefer the latter when adding tests — stale data
in the fixed directories has caused confusing failures.

## What this library does

Serializes `Glob`s into flat, fixed-stride records in memory-mapped files, addressed by byte offset, and
reads them back with zero copying beyond the `Glob` instance itself. Everything is derived from the
`GlobType` at startup; the per-record path is an array walk over precomputed byte offsets.

Two independent storage families share the same layout/field machinery:

- **tree** (`mem/tree`) — write-once. `OffHeapTreeService.create(type)` → `declareUniqueIndex` /
  `declareNotUniqueIndex` → `createWrite(dir).save(globs)` → `createRead(dir, arena)`. Indexes are
  *implicit binary search trees* flattened to disk (see below).
- **hash** (`mem/hash`) — hash-table with in-place update. `OffHeapHashService.create(type)` →
  `declare(name, keyBuilder, size)` → `createWriter` / `createReader` / `createUpdater`. Records get an
  extra leading `long` slot (`__FreeId__`, injected via `OffHeapGlobTypeGroupLayoutImpl.create(type, withFirstLayout)`)
  used as a free/tombstone timestamp so the updater can recycle slots.

`mem/` at the root holds what both use: `DataSaver` (the writer), `DefaultOffHeapReadDataService` (the
reader, which is also the `ReadContext` handed to every field accessor).

## The layout pipeline

Startup, once per `GlobType`:

1. `DataSaver.extractTypeWithVarSize` walks the type graph and collects every reachable type. Types reached
   through a `GlobField`/`GlobArrayField` *without* `@HeapInline` are **separate files**; with `@HeapInline`
   they are embedded in the parent's record.
2. `GroupLayoutFieldVisitor` (a `FieldVisitor`) turns the fields into a `java.lang.foreign.GroupLayout`,
   inserting explicit padding itself and naming each member after the field. Composite kinds get several
   named members, using the suffix constants on `DefaultOffHeapTreeService` (`_len_`, `_addr_`, `_set_`,
   `_date_`/`_time_`/`_nano_`/`_zoneId_`). Cycles are rejected.
3. `OffHeapTypeInfo.create` switches once per field to build a `HandleAccess[]`, each holding the byte
   offsets resolved from the layout. `RootOffHeapTypeInfo` = primary layout + the inline sub-layouts.

Runtime: `save`/`readAtOffset` loop over `HandleAccess[]` at a record offset. Nothing reflects, nothing
re-resolves a handle. `IndexTypeBuilder` does the same for index records, but with `DataAccess`
(`compare` against a `FunctionalKey` directly in the segment, no `Glob` materialized) instead of
`HandleAccess`.

`OffHeapTypeInfo.byteSizeWithPadding()` — not `byteSize()` — is the record stride; record *n* lives at
`n * byteSizeWithPadding`.

## What a read costs

Measured with `ReadPerf`, four types, narrow / wide: the index descent is **2.67 M / 2.69 M ops/s** and
materializing one Glob is **3.91 M / 1.54 M**. On a narrow record `find` and `read` now cost about the same;
on a wide one `read` is still where the time goes. Optimize the read path, not the descent.

**No `VarHandle` on the record path.** Every `HandleAccess` resolves its byte offset once, at `create` time,
with `groupLayout.byteOffset(PathElement.groupElement(name))`, and reads through
`memorySegment.get(ValueLayout.JAVA_INT, offset + fieldOffset)`. This is not cosmetic and it is the single
biggest thing measured here: **`read` 1867 k → 3913 k (narrow) and 619 k → 1535 k (wide)**, `readAll` +91 % /
+76 %, while `find` — untouched, and therefore the control — moved 5-8 %. The reason is that the
`HandleAccess[]` loop is megamorphic, so the receiver is not a JIT constant, so a `VarHandle` held in one of
its fields is not a constant either and the access falls off its intrinsic path; a `ValueLayout` constant plus
an offset add does not care who the receiver is. Note what this says about the dispatch itself: the call site
is exactly as megamorphic as before, and the read still doubled.

The index side (`field/dataaccess`) **keeps its `VarHandle`s** — it addresses a record inside a sequence, and
the offset is not known before the descent. That is why `FixSizeStringFieldHandleAccess` carries two length
readers: `RecordLen` (offset-based, record path) and `ReadLen` (`VarHandle`-based, index path, with
`readLenArray`).

Four field readers used to walk the segment **one element at a time through an indexed `VarHandle`**, which is
what made a read cost 6.2 µs instead of 0.39 µs (on the old single-type harness, `read` went from 162 k to
2537 k ops/s). All four now do a single `MemorySegment.copy`, which needs the same base offset next to it —
an indexed `VarHandle` could only ever hand over one element.

- fixed-size strings (`@MaxSize`), both kinds — they also built a `StringBuilder`, which allocated a buffer
  and then copied it again in `toString()`. The `Heap7BitsString` variant decodes with `ISO_8859_1`: `save`
  writes `codePointAt(j) & 0xFF` and the old loop read back `(char) (c & 0xFF)`, which *is* Latin-1, and it is
  the compact-String fast path.
- `IntArrayFieldHandleAccess`.
- the zone id of a `DateTimeField` — 52 `VarHandle` calls, and then `ZoneId.of(new String(...))` **on every
  read**. It now keeps a one-entry memo of `(raw bytes, ZoneId)`, compared on the bytes so a hit costs neither
  the String nor the lookup; records almost always share a zone. It is a `volatile` immutable pair, so a race
  recomputes rather than publishing something half-built.
- `DefaultOffHeapReadDataService.get`, the interned-string decode — only on a cache miss, but a miss is every
  string the first time the data is walked.

`BulkReadRoundTripTest` is the guard: empty and full-width strings, a byte above 127 on the "7 bits" kind,
null vs empty, and **alternating zone ids** (long then short, so a stale memo cannot match on a prefix).
### The generated walk

`readAll` without the `onlyFields` predicate — and only that path — can build its walk as a class emitted by
globs-generate instead of the loops of `PartitionedGlobReader`: the `HandleAccess[]` unrolled into one call
site per field, each reading its accessor from a `static final`, so the receiver is a JIT constant there.
`GeneratedWalkReader` builds it, `OffHeapTypeInfo.walkReader` holds it (the partitioned reader itself when
nothing generates), and `ReadAllPerf` is the benchmark, with a `caller` param JMH forks a JVM for.

**Nothing is adapted, and that is the whole design.** The emitted class implements `GlobReader` itself and
calls `HandleAccess.readAtOffset` itself, through core's typed factory shape —
`create(name, functions, GlobReader.class, HandleAccess.class, MutableGlob.class, MemorySegment.class,
long.class, ReadContext.class)`. The two interfaces were written independently and their methods are not even
named alike, but they take the same parameters, which is what that shape matches on. So there is no wrapper
object, no generic bridge, no checkcast, no boxed offset: one LLOAD for the offset, and the generated class
*is* the reader rather than something holding one.

| `readAll`, 5 forks × 5 iterations | partitioned | generated | |
| --- | --- | --- | --- |
| narrow, 15 fields | 415.3 ± 6.4 | **462.9 ± 6.8** | **+11.5 %** |
| wide, 45 fields | **145.7 ± 1.6** | 130.4 ± 0.7 | **−10.5 %** |

`read` — one record, on the partitioned reader in both arms — is the control and does not move
(4412 k / 4476 k narrow, 1781 k / 1773 k wide).

**What the shape is worth**: the same walk through `ToGlobFunction`, i.e. with the adapter and the boxed
offset, measured 405.2 narrow and 114.1 wide. Dropping the adaptation is **+14 %** on both, and it is what
turns narrow from noise into a win. The counters say why, and they say it cleanly — the generated arm now
runs **fewer instructions than the partitioned one** (103.7 M against 106.9 M per pass; through
`ToGlobFunction` it was 116.2 M), and its icache misses are *lower* too (1 592 against 3 414; the adapter
classes were what polluted it, 9 152). Two explanations died there: the adaptation was the cost, not the
inlining budget (the chunk below) and not the size of 45 inlined bodies.

**What is left on wide is pure IPC**: 3.087 → 2.653 over the same instruction stream, i.e. 13 % more cycles
for slightly less work, with branch misses up 59 % (worth about a seventh of the gap). A long straight line
decodes worse than a short hot loop — µop cache residency, which no icache counter shows — and that is not
something the API can fix.

**So whether unrolling wins depends on the type, and predictably so.** A loop per kind amortizes *one*
inlined body over every field of that kind; unrolling needs one per field. Narrow is 15 fields over ~14
kinds, so each loop runs once and its overhead dominates: unrolling wins by 11.5 %. Wide is three fields per
kind, the loop amortizes, and unrolling loses by 10.5 %. Fields per kind is the number to look at before
adopting this for a type — it is not a global answer.

**The chunk does not rescue the wide shape** (`-Dglobs.caller.toGlob.chunk=<n>`, added to globs-generate for
this, and which the typed shape does not implement — it always emits one method). Measured on the earlier
`ToGlobFunction` walk: 113.9 ± 1.7 for one method against 114.3 ± 8.5 for chunks of 12, the same number with
five times the spread. Inlining is decided from the compilation root and is transitive, so splitting the
emitted method does not reduce how much code sits under that root.

**Two `-XX:CompilerDirectivesFile` files in `src/test/resources`** settled what the loss was *not*, back when
it was 19 %: `deinline-cheap-accessors.json` puts the partitioned arm into the generated arm's compilation
state and costs 2.5 %, `dontinline-big-accessors.json` frees the generated arm's inlining budget and changes
nothing. Run either with
`-jvmArgsAppend "-XX:+UnlockDiagnosticVMOptions -XX:CompilerDirectivesFile=src/test/resources/<file>"`. The
unlock flag has to come first, and HotSpot's parser takes **exactly one** comment line, at the very top of
the file — a second one, or one inside the JSON, is a syntax error.

The walk is generated **only** when `-Dglobs.caller.toGlob=…AsmCallerWriteGeneratorService` installs a
generating factory; `ToGlobCallerFactory.generated()` answers null otherwise and `walkReader` is the
partitioned reader, unchanged. Core's looped factory is deliberately not a fallback — its typed shape is a
reflective proxy, slower than anything here. globs-generate is a **test** dependency: main code only names
core's SPI.

One consequence of having no wrapper left: the four Glob-valued kinds are now called through a constant
receiver like every other, so the descent into a sub-record is foldable, where the `ToGlobFunction` version
deliberately kept an ordinary class in front of them as an inlining barrier (globs-bin-serialisation measured
−12 % for folding that descent). No type in `ReadAllPerf` has a nested Glob, so this benchmark says nothing
about it.

Still on the table, in rough order of what a profile says:

- splitting the `HandleAccess[]` walk per field kind is **done** — `PartitionedGlobReader`, one monomorphic
  loop per kind instead of one megamorphic call site for the ~14 implementations. What is left of that cost
  is the missed inlining, and "The generated walk" above says what removing it is worth.
- picking the walk per type rather than per process: the generated one wins on a type whose fields are spread
  over many kinds and loses on one with several fields per kind (+11.5 % / −10.5 % here). `OffHeapTypeInfo`
  has both readers at hand and knows the field kinds, so the choice is a ratio away — what is missing is
  shapes between 15 and 45 fields to put the threshold somewhere honest.
- `readStrings` is a `Map<Integer, String>`, so every interned-string read boxes its address (`IntHashMap` is
  already imported there, unused).
- every scalar field is boxed on its way into `DefaultGlob`'s `Object[]` — `GlobSetIntAccessor.set` takes an
  `Integer` and `setNative` is a `default` that just calls it. This is the one place globs-generate's
  *primitive* flavour would pay, and only a setter-side generated caller would collect it; the
  `GlobInstantiator` is injectable.
- `read(offset, Predicate<Field>)` already exists and is the cheapest win for a caller that only wants a few
  fields of a wide record.

## Encoding conventions to preserve

- **`isSet` vs `isNull` are encoded in sentinel values**, per field kind: strings write `-2` in the length
  slot for unset and `-1` for null; glob references write `-2L`/`-1L` in the offset slot; inline globs use a
  `_set_` byte (1 null, 2 unset). Any new `HandleAccess` must keep the distinction — round-tripping depends
  on it.
- **Strings are interned into one `strings.data` file**: `[int len][utf8 bytes]` repeated; records store
  `(addr, len)` and the reader caches decoded strings by address. `@MaxSize` strings are instead stored
  inline as a fixed `char[]` (or `byte[]` with `Heap7BitsString`) with no entry in the string file.
- **Annotations that drive layout** live in `mem/model` and follow the workspace's Glob-annotation pattern
  (`TYPE`/`UNIQUE_KEY`/`UNIQUE_GLOB`): `HeapInline` (embed instead of reference), `HeapMaxElement`
  (**required** on every `GlobArrayField` — its `maxSize` fixes the array stride), `Heap7BitsString`.
  Core `@MaxSize` and `@ArraySize` are also read.
- Files in a storage directory: `content.data_<TypeName>` (one per type, plus a `_<indexName>` suffix for
  hash index tables), `strings.data`, `<indexName>Unique.data`, `<indexName>Many.data`.

## Index representation

`DefaultOffHeapWriteTreeService` sorts keys into a `TreeMap` with `IndexFunctionalKeyComparator`, splits the
sorted array recursively (`Utils.split1Element`) into a balanced tree, numbers the nodes in pre-order, then
writes one index record per node holding: the key fields, `dataOffset1`, `dataLenOffset1`, and
`indexOffset1`/`indexOffset2` = the *record numbers* of the children (`-1` for none). Reading is a recursive
descent over those child numbers, comparing key fields in place.

`dataOffset1` is overloaded on the multi index: when `dataLenOffset1 == 1` it is the data offset directly,
otherwise it is an offset into `<indexName>Many.data`, an array of `len` data offsets. Unique indexes always
write `len == 1`.

`search(...)` (prefix search on the first *n* key fields) differs from `find(...)`: it descends with an
`EqualAt` (BOTH/LEFT/RIGHT) marker to collect the whole matching range, and applies a `Filter` for key
fields past the prefix.

## Adding a field kind

A new supported `DataType` needs, in order: a `visitXxx` in `GroupLayoutFieldVisitor` (with its padding), a
`HandleAccess` in `field/handleacces` (`create(GroupLayout, XxxField)` + `save` + `readAtOffset`, plus
`scanOffset` if it holds references to other records), a case in `OffHeapTypeInfo.create`, and — if it can
be an index key — a `DataAccess` in `field/dataaccess` plus a case in `IndexTypeBuilder` (which otherwise
falls back to `AnyDataAccess`). Fields also need to be handled in `DataSaver.extractGlobToSave` /
`scanForString` when they can contain nested globs or strings.

## Arenas and lifecycle

The caller owns the `Arena` and passes it to `createRead`/`createReader`/`createUpdater`; the services map
files into it and never create their own (`a4ddde0` deliberately removed a per-index arena). `FileChannel`s
are closed right after `map` — the mapping outlives them. Closing the arena invalidates every `Glob` field
still pointing into a segment, so a read service must not outlive its arena.
